This chapter reports the state of the project in November 2026. The results come from a small development set (six engines) and are a first look, not a conclusion.

The question

An aircraft engine is monitored flight after flight. At a given flight t, an engineer asks:

Based on the information available up to flight t, is there evidence of a concerning trend? What are the plausible causes, and what check should be recommended?

Three situations are possible: gradual ageing (normal), compressor fouling (needs an engine inspection) and sensor drift (needs a sensor check, not an engine inspection). The task is to build an agent: a language model that reads the documentation, decides which diagnostic tools to call, and writes a justified recommendation. It must be able to say “insufficient information” and must never treat a tool’s output as a definitive diagnosis.

What I built

library(tidyverse)
library(here)
library(scales)
library(knitr)

theme_set(theme_minimal(base_size = 12) +
            theme(plot.title.position = "plot",
                  panel.grid.minor = element_blank(),
                  legend.position = "top"))

phm_dir <- here("data", "safran")

1. A rule-based baseline without an LLM. Alert when the exhaust-gas temperature margin (1150 K minus the LPT inlet temperature) stays below a threshold for p consecutive usable flights. The persistence rule avoids alerting on one noisy flight. The supervisors suggested a threshold of 11.5 K; I swept threshold and persistence over a grid on the development trajectories, then evaluated the chosen setting once on held-out test trajectories.

2. A single tool-using agent (LangChain + Ollama, temperature 0) with four tools bound to one engine and cut at the decision time, so the model physically cannot look into the future:

Tool What it returns
lire_observations(debut, fin) sensor readings and flight conditions, ≤ 30 flights per call
estimer_sante(debut, fin) six health indicators estimated by a pretrained inverse MLP
calculer_marge(debut, fin) the thermal (EGT) margin per flight
regle_seuil_marge() (optional) the baseline rule’s verdict, as one more piece of evidence

The agent receives the knowledge base as its system prompt and must answer with one of five actions: continue monitoring, intensify monitoring, request an engine inspection, request a sensor check, or request additional data.

3. A fair evaluation harness. Every model gets the same tools, documents, prompt, decision time and step limit. Each run records the recommendation, the number of tool calls, the duration and the full reasoning trace (JSON lines). The expected action is derived from the hidden scenario labels by the evaluator only; the agent never sees them.

The baseline: a trade-off between speed and false alarms

grid <- read_csv(file.path(phm_dir, "baseline_grid_dev.csv"), show_col_types = FALSE)
chosen <- filter(grid, seuil_marge == 11.5, persistance == 3)

grid |>
  filter(fouling_detection >= 0.9) |>
  ggplot(aes(normal_fausse_alerte, fouling_retard_median, colour = factor(persistance))) +

  geom_point(data = chosen, shape = 21, size = 6, colour = "#D55E00", stroke = 1.2) +
  annotate("text", x = chosen$normal_fausse_alerte + .03, y = chosen$fouling_retard_median + 6,
           label = "chosen: 11.5 K, 3 flights", hjust = 0, colour = "#D55E00", size = 3.4) +
  scale_x_continuous(labels = label_percent()) +
  scale_colour_viridis_d(end = .85) +
  labs(x = "False alarms on healthy engines", y = "Median detection delay\nfor fouling (flights)",
       colour = "Persistence (flights)")

test |>

Requiring persistence pays off (Figure 6.1). On the test engines, the chosen rule detects every fouling case with 3% false alarms on healthy engines, against 61% without persistence (Table 6.1). Its limits are structural: it detects fouling a median of 106 flights after it starts, and it has no way to tell sensor drift from real degradation. It can only say “inspect the engine” or “keep monitoring”. That gap is the reason to try an agent.

What the first runs show (Figure 6.2, Table 6.2):

  • Plumbing matters first. In run 1, most models produced no usable answer. Reading the traces showed why: models asked for flights after the decision time, the tool raised an exception, and the run died. Returning tool errors to the model as text (“window outside the authorised history, correct the arguments”) let it recover; in run 2, qwen3:8b answered every case.
  • The agent is cautious where the baseline is blind. On both sensor-drift engines, qwen3:8b recommended intensify monitoring (acceptable) where the baseline said “all fine”. But it also missed both fouling cases, while the baseline caught one.
  • Cost. About 15 tool calls and four to five minutes per case with a local model, against an instant rule.

So far, the agent is not better than a tuned rule on raw accuracy. The next question is whether it adds value on top of the rule.

Next steps

  • Give the agent the baseline rule as a tool (already implemented, flag --with-baseline-tool) and measure whether it combines the rule’s fouling detection with its own caution on drift.
  • Add trend and change-point tools, so the model does not have to spot a slow drift by reading 30-row tables.
  • Evaluate on more engines and several decision times, and score the justification (evidence cited, alternatives considered), not just the final action.
